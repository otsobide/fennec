### 1.3 The algorithm (exact code path)

`generateStandardId(type, data)` (`GQL/src/schema/identifier.js:509-522`): for `isStixCyberObservable(type)` it calls `generateStixId(type, data)` (line 513), which is:

1. `generateDataUUID(type, input)` (lines 415-447):
   - `data = { ...input, opencti_type: type }` (line 416). The `opencti_type` key is only used by resolvers (Software) and never ends up in the hashed JSON for observables because only `src` keys of the "way" are picked.
   - Looks up the contribution definition for the type (lines 417-421; `resolveContribution` lines 323-330).
   - If the definition is a function, call it (random UUIDv4 types; none are observables) (lines 423-425).
   - If the definition is an **array of arrays**, it is a list of alternative **"ways"**: try each in order and stop at the first that yields non-empty data (lines 431-441). Otherwise a single way (lines 442-445).
2. `filteredIdContributions(contrib, way, data)` (lines 384-413):
   - `R.pick(propertiesToKeep, data)` keeps only the `src` keys of the way (lines 385-386). If nothing is present, return `{}` (lines 387-389).
   - For every present key, find its definition with `R.find((e) => R.includes(key, e.src), way)` (line 395). Note: Ramda `includes` on strings is a **substring test**; correct today only because no `src` of a given type is a substring of an earlier `src` in the same way **[INF]**.
   - If any `dependencies` of that property is empty in `data`, **the whole result becomes `{}`** (lines 397-401), not just that property.
   - Output key is `dest || src` (line 402). The definition key must be spelled `dest`; a `dst` key is ignored (see Windows-Registry-Key, 1.6).
   - If a resolver exists **for the `src` name** in the contribution's `resolvers`, apply it as `resolver(value, data)` when the value is truthy (lines 403-407); otherwise strings are `.trim()`-ed and other values pass through unchanged (line 409).
   - Finally drop keys whose value is `R.isEmpty` or `R.isNil` (empty string, empty array, empty object, null, undefined) (line 412).
3. `idGen(type, dataUUID, OASIS_NAMESPACE)` (lines 331-347):
   - Empty data throws `FunctionalError("Missing required elements for <type> creation (<src - src - ...>)")` (lines 333-338).
   - `jsonCanonicalize(data)` from the npm `canonicalize` package (import at line 4, call at line 345), then `uuidv5(canonical, namespace)` (line 346).
4. Prefix: `${convertTypeToStixType(type)}--${uuid}` (line 498). `convertTypeToStixType` (`GQL/src/database/stix-2-1-converter.ts:137-160`) lowercases the internal type, with special cases `StixFile -> file`, identity/location/threat-actor families, relationship/sighting.

Canonical serialisation: the `canonicalize` package is an RFC 8785 (JSON Canonicalization Scheme) implementation: keys sorted lexicographically (by UTF-16 code units), no whitespace, ES6 number formatting, minimal string escaping **[MEM]**. For the ASCII strings and integers used by observable ids, Python `json.dumps(d, sort_keys=True, separators=(',', ':'), ensure_ascii=False)` produces byte-identical output, which is how the examples in 1.8 were recomputed **[VER]**.

Important property: the hashed JSON never contains the type. Two different types with the same canonical JSON share the same UUID part, only the prefix differs. Example: `hostname--3b96539c-807f-59c9-b4df-fe1865757b1e` and `domain-name--3b96539c-807f-59c9-b4df-fe1865757b1e` both come from `{"value":"www.example.com"}` **[VER]**. Any identity store must key on the full prefixed id, or on `(type, uuid)`, never on the bare UUID.

### 1.5 Hash handling (File, Artifact, X509-Certificate)

- Algorithm constants: `MD5`, `SHA-1`, `SHA-256`, `SHA-512`, `SHA3-256`, `SHA3-512`, `SSDEEP`, `SDHASH`, `TLSH`, `LZJD` (`GQL/src/schema/identifier.js:28-37`). Fuzzy subset: `FUZZY_HASH_ALGORITHMS = ['SSDEEP', 'SDHASH', 'TLSH', 'LZJD']` (`GQL/src/schema/fieldDataAdapter.ts:13`).
- Key normalisation: input `[{algorithm, hash}]` becomes a dictionary with `d.algorithm.toUpperCase().trim()` as key and `d.hash.trim()` as value (`GQL/src/schema/fieldDataAdapter.ts:29-37`), called in `addStixCyberObservable` (`GQL/src/domain/stixCyberObservable.js:239-241`). There is **no alias mapping**: `sha256` becomes `SHA256`, which is neither recognised by the id resolver nor allowed by the strict ES mapping (sub-fields are exactly the 10 names, `GQL/src/modules/attributes/stixCyberObservable-registrationAttributes.ts:55-76`) **[INF]**.
- Hash **values are not lowercased** anywhere before hashing: `46C293...` and `46c293...` give different standard_ids. The integration test creates an Artifact with upper-case hashes and expects them preserved (`GQL/tests/03-integration/02-resolvers/stixCyberObservable-test.js:168-224`). Example: `{"hashes":{"MD5":"d41d8..."}}` -> `file--02fff920-...`, upper-case -> `file--79550d64-...` **[VER]**.
- Id resolver (`GQL/src/schema/identifier.js:157-172`): upper-cases the keys of the stored dictionary (`transformObjectToUpperKeys`, lines 38-40), then returns **a single-entry dictionary** with the first available algorithm in this exact precedence:

  `MD5 > SHA-1 > SHA-256 > SHA-512 > SHA3-256 > SHA3-512 > SSDEEP > SDHASH > TLSH > LZJD`, else `undefined` (then the next "way" is tried).

  [MEM] The `stix2` python library's `_choose_one_hash` uses MD5 > SHA-1 > SHA-256 > SHA-512 and then the first remaining key; the spec text lists a similar preference order. For the four main algorithms OpenCTI and `stix2` agree; they can diverge only for objects whose best hash is SHA3/fuzzy.
- Per-hash ids: `generateHashedObservableStandardIds(instance)` computes `generateStandardId(type, { hashes: { [k]: v } })` for **every** hash entry, fuzzy included (`GQL/src/schema/identifier.js:546-562`; test asserting every fuzzy algorithm produces an id: `GQL/tests/01-unit/domain/identifier-test.js:386-394`). On create, all of them except the chosen standard_id are appended to `x_opencti_stix_ids` (`GQL/src/database/middleware.ts:3971-3980`). On update the list is recomputed (`GQL/src/database/middleware.ts:2410-2435`).
- Lookup by hash on create/update: `listEntitiesByHashes` does an `AND` filter `hashes.*` with operator `wildcard` on the **non-fuzzy** hash values only (`GQL/src/database/middleware.ts:1547-1568`, `extractNotFuzzyHashValues` in `GQL/src/schema/fieldDataAdapter.ts:21-26`). The wildcard filter becomes a `query_string` phrase query on the text fields (`GQL/src/database/engine.ts:2522-2530`), so it is case-insensitive **[INF]**.
- Raw hash values are also used as **Redis lock resource names** (`getHashIds`, `GQL/src/schema/identifier.js:564-573`, added in `getInputIds` line 599), so two concurrent creations sharing a hash serialise.
- Merge safety: `hashMergeValidation` throws `ValidationError('Hashes collision', 'hashes_<ALGO>')` if two instances to merge have different values for the same algorithm (`GQL/src/database/middleware.ts:1569-1584`). It compares raw strings, so case variants of the same hash would be reported as a collision **[INF]**.
- Inconsistency **[INF]**: fuzzy-hash ids participate in id-based matching (via `generateHashedObservableStandardIds` in `getInputIds`, line 600, and via `x_opencti_stix_ids` of existing objects), although `listEntitiesByHashes` explicitly excludes fuzzy hashes. Two different files sharing only an SSDEEP/TLSH string can therefore be matched (single match: upsert into the other file; multiple: merge then `Hashes collision`).

### 1.10 Create / upsert / merge decision procedure (observables)

`internalCreateEntityRaw` (`GQL/src/database/middleware.ts:3899-4227`), condensed:

1. Resolve all refs (ids -> full stored elements) (`inputResolveRefs`, line 3948; function 1074-1270).
2. `participantIds = getInputIds(type, resolvedInput)` (line 3951; `GQL/src/schema/identifier.js:587-608`): computed standard_id, `internal_id`, `stix_id`, `x_opencti_stix_ids`, alias ids, raw hash values, per-hash standard_ids.
3. **Redlock** on all participant ids (line 3956; `GQL/src/database/redis.ts:434-522`, keys `{locks}:<id><draftId>`, defaults `retry_count 100`, `retry_delay 250ms`, `retry_jitter 100`, `max_ttl 60000ms`, `extension_threshold 5000` from `GQL/config/default.json:112-118`). After acquiring, the lock fails if any participant was deleted in the last 5 s (`platform-deletions` sorted set, `GQL/src/database/redis.ts:396-413,484-490`).
4. Compute standard_id (line 3958) and search existing by all ids (`internalFindByIds`, line 3962) plus, for hashed types, by any non-fuzzy hash (lines 3967-3970). Hashed types force `update = true` (line 3970).
5. Branches (lines 3995-4114):
   - 0 found: build and index new document (lines 4117-4207), then push `create` event (line 4216).
   - exactly 1 found: `upsertElement` into it (lines 4023-4030).
   - several found, non-hashed, one has the computed standard_id: if `stix_id` points to another one, **auto-merge** (target = higher confidence) then upsert (lines 4033-4091).
   - several found, hashed (`update === true`): `hashMergeValidation`, then **merge all into** the one whose standard_id equals the computed one (else the first), then upsert (lines 4092-4102).
   - otherwise upsert into the one carrying `stix_id` or the first (lines 4104-4114).
6. Upsert policy: an attribute is overwritten only if `confidence_to_apply >= existing.confidence`, the attribute is declared `upsert: true` and the input is non-empty; or the current value is empty; or full-sync mode (`GQL/src/utils/upsert-utils.js:529-561`; confidence computed in `GQL/src/utils/confidence-level.ts:125-143`).
7. An update that would change the standard_id to one already owned by another observable triggers a merge (observables) or an error "This update will produce a duplicate" (other types) (`GQL/src/database/middleware.ts:2665-2722`).
8. Merge (`mergeEntities`, lines 2031-2109): lock all, load target and sources, redirect all relationships and merge attributes (`mergeEntitiesRaw`, lines 1657-1969: relation redirect from 1727, attribute merge in the last part of the function up to `elUpdateElement` at 1966), push one `merge` event (line 2094), record source ids as recently deleted (line 2096). For File/Artifact, upserted names are pushed to `x_opencti_additional_names` instead of being lost (lines 2374-2393).

### 3.2 Mappings and settings

- **One global mapping** generated from all attributes of all types, applied to every index template (`engineMappingGenerator`, `GQL/src/database/engine-mapping-generator.ts:22-24,107-115`), with `dynamic: 'strict'`, `date_detection: false`, `numeric_detection: false` (`GQL/src/database/engine.ts:1254-1262`). Template per alias pattern, `composed_of: [opencti-core-settings]` (lines 1243-1279).
- String mapping (`GQL/src/schema/attribute-definition.ts:12-25`): short strings are `text` + `keyword` sub-field with `ignore_above: 512` and `normalizer: 'string_normalizer'` = `lowercase` + `asciifolding` (`GQL/src/database/engine.ts:1182-1189`). Consequences: keyword equality is case- and accent-insensitive; values longer than 512 chars (long URLs, command lines) are not keyword-indexed **[INF]**. Long strings (`text`, `json` formats) are plain `text`. Numbers `coerce: false`.
- Objects: `standard` objects get strict sub-mappings (e.g. `hashes` with exactly 10 algorithm sub-fields), `flat` objects use `flattened` (ES) / `flat_object` (OpenSearch), `raw` objects `enabled: false`, `nested` for nested (`engine-mapping-generator.ts:46-67`).
- Denormalised relation fields: for every relationship type `rel_<type>` with `internal_id` and `inferred_id` keyword arrays (`engine-mapping-generator.ts:86-105`). Rule inferences: `i_rule_<id>` objects (lines 70-85).
- Limits: `mapping.total_fields.limit = 3500` (`max_mapping_fields`, `engine.ts:231,1214-1222`), `max_result_window 100000` (219), pagination default 500 / max 5000 (212-213), bulk max 5000 ops (214), `ES_RETRY_ON_CONFLICT = 30` (229), bulk timeout `1h` (230).
- Lifecycle: ILM policy `opencti-ilm-policy` (ES) or ISM `opencti-ism-policy` (OpenSearch), hot phase rollover at `max_primary_shard_size 50gb` or `max_docs 75000000` (`engine.ts:223-224,1096-1169`). Shards/replicas from config (220-221, 1176-1181).

### 3.3 Document shape and lookups

- `_id` = `internal_id`; the concrete backing index is remembered on every loaded doc as `_index` and is required for updates (`engine.ts:4867,4928`; `engine-data-converter.ts:87-92`).
- Relationship documents carry a nested `connections` array of both ends: `internal_id`, representative `name`, `types` (type + parent types), `role` (`engine.ts:4666-4721`).
- Entities carry denormalised `rel_<relationship>.internal_id` arrays of the other end, appended via a single parametrised painless script (`EL_DENORMALIZED_REFS_SCRIPT_SOURCE`, `engine.ts:4780-4798`; applied 4876-4937). Script fields are parameters precisely to avoid exhausting `script.max_compilations_rate` (comment 4777-4779).
- Super-node protection: some sides are deliberately not denormalised: `created-by`, `object-marking`, `object-assignee`, `object-participant`, `granted`, `object-label`, `kill-chain-phase` on the "to" side, `publishes` on "from", `in-pir`, `indicates` "to" (`engine.ts:236-249`), and `related-to` from an observable on the "to" side, "to avoid for instance Emotet having 200K related-to" (lines 253-258), and `located-at` IP/City -> Country/Region (259-264).
- Id lookup: `elFindByIds` builds `terms` on the four id keyword fields, splits ids by `max(ES_MAX_PAGINATION/2, 500)` per query and throws if a query returns `>= 5000` docs (duplicated ids) (`engine.ts:1664-1788`).

### 3.4 Write path and consistency

- Writes: `elIndexElements` bulks with `refresh: true` (`engine.ts:4873,4933`; also `elUpdate` 4109, `elDelete` 4159). Every write forces a refresh so that the search-based dedup sees it immediately.
- No uniqueness constraint exists in the search engine (and `_id` uniqueness is per backing index only, while rollover creates several). Uniqueness of `standard_id` relies on: Redis Redlock over all candidate ids, then a search, then insert (section 1.10) **[INF]**.
- Not atomic: index write (`indexCreatedElement`, `GQL/src/database/middleware.ts:4207`) happens before the stream XADD (`storeCreateEntityEvent`, line 4216). A crash in between loses the event; the merge code labels this block "TRANSACTION PART" but there is no transaction (`middleware.ts:2087-2097`) **[INF]**.
- Merges physically rewrite every relationship of the sources (redirect `from`/`to`, delete duplicates) (`middleware.ts:1657-1760` and onwards); cost grows with the degree of the merged nodes.

### 3.6 Live stream over HTTP (SSE)

Routes: `GET /stream` (raw, authenticated), `GET /stream/:id` (live stream collection, can be public), `POST /stream/connection/:id` (`GQL/src/graphql/sseMiddleware.js:1058-1061`).

- Wire format: `id: <redis id>\nevent: <type>\ndata: <JSON envelope>\n\n`; `granted_refs` stripped for users without the organisation-restrict capability (`sseMiddleware.js:504-526`). Heartbeat events every 5 s plus `consumer_metrics` (lines 77, 570-594).
- Resume parameters (lines 826-836): `from` / `Last-Event-ID` / `from` header (stream id `ms-seq`, `0`, or an ISO date converted to `<ms>-0`, lines 784-818), `recover` (date up to which the history must be rebuilt from the database), `no-dependencies` (alias `no-relationships`), `listen-delete=false`, `with-inferences=true`.
- Filtering semantics (lines 859-979): each event is evaluated against the collection filters both **before** (previous state reconstructed by applying `reverse_patch` to `data`, line 889) and **after** the change:
  - previously visible, now not: emitted as `delete` with the previous document and empty context (891-899);
  - previously not visible, now visible: emitted as `create` with empty context, after publishing missing dependencies (900-910);
  - visible both times: `update` (911-919);
  - not visible relationship: may be published as a dependency if one end matches (920-923, 742-783);
  - not visible entity that belongs to a matching container: published (924-945).
- Dependency resolution: before publishing an object, missing referenced objects (refs, relationships' ends, container contents) are loaded and sent as `create` events with `origin.referer = 'init-dependencies'`, with an LRU cache of already-sent ids (5000 entries, 1-2 h) (lines 75-80, 282-424, 653-709).
- Recovery: when `recover` is given with `from`, the platform queries Elasticsearch for objects matching the filters with `updated_at` between the two dates and emits synthetic `create` events (`origin.referer = 'init-create'`, event id derived from `updated_at`), then starts live consumption from the recover point (lines 986-1041). Deletions inside the recovered window are not replayed **[INF]**. Recovery is skipped for streams with origin filters (987-1002).

### 3.7 RabbitMQ ingestion and workers

- Exchanges: `amqp.connector.exchange` and `amqp.worker.exchange`, both `direct` and durable (`GQL/src/database/rabbitmq.js:14-15`; `GQL/src/modules/connector/connector-rabbitmq.ts:98-100`). Optional queue prefix `rabbitmq:queue_prefix` (`GQL/src/database/utils.ts:27-28`).

- Message (worker side, `WRK/src/push_handler.py:83-118`): JSON with `content` (base64 STIX bundle or event), `type` (`bundle` or `event`), `applicant_id`, `work_id`, `playbook_id`, `event_id`, `draft_id`, `synchronized`, `previous_standard`, `update`, `no_split`, `entities_types`.
- Splitting: platform-side `pushBundleToWorker` splits multi-object bundles with `Stix2Splitter` into **one object per message**, ordered by dependency count (`nb_deps`, computed by walking every `*_ref`/`*_refs`), sets `no_split: true`, and increments the work's expected count (`GQL/src/database/rabbitmq.js:517-569`; `GQL/src/utils/stix2-splitter.ts:169-349`). The worker re-splits if it receives an unsplit multi-object bundle (`push_handler.py:161-204`).
- Worker processing: `prefetch_count=1` per consumer thread (`WRK/src/message_queue_consumer.py:23`), thread pools for normal/realtime queues (`WRK/src/worker.py:229-241`). Each object goes through pycti `import_item` -> GraphQL mutation (`stixCyberObservableAdd` for SCOs) -> `createEntity` above. Events of type `event` (sync) are translated into single-object bundles; `merge` uses `context.sources` ids (`push_handler.py:207-262`).
- Retries (`PY/pycti/utils/opencti_stix2.py:3796-3928`): lock errors retried with 1-3 s jitter, connection timeouts with 10-30 s, bad gateway / timeout 60 s, missing references retried a bounded number of times (the platform itself rejects twice before accepting a missing optional ref, `GQL/src/database/middleware.ts:1241-1250`), then the item goes to the dead letter queue with `rejection_info`.

### 3.8 Scalability limits and design choices (OpenCTI facts, then assessment)

| # | OpenCTI choice (fact) | Effect | For Fennec **[REC]** |
|---|---|---|---|
| S1 | Dedup = Redis Redlock on candidate ids + search + insert; no DB uniqueness (1.10, 3.4) | Lock contention under load (workers retry indefinitely on lock errors), duplicates possible if lock TTL (60 s) expires; delete/recreate race patched with a 5 s "recent deletions" set | Avoid. Use PostgreSQL unique constraints on `standard_id` and on an alternate-id table, `INSERT ... ON CONFLICT`, and transaction-scoped advisory locks only for multi-row merges |
| S2 | `refresh: true` on every bulk/index/update (3.4) | Throughput bounded by refresh cost; needed only because dedup reads the search index | Avoid; PG gives read-your-writes inside the transaction |
| S3 | Index write then XADD, not atomic (3.4) | Lost or phantom events on crash | Avoid. Transactional outbox table written in the same transaction as the aggregate change |
| S4 | All observable types in one index with one global strict mapping, 3500-field cap (3.1-3.2) | Every new attribute of any type consumes the shared field budget; sparse documents | Per-type tables with typed columns (matches the "no generic types" rule) |
| S5 | Denormalised `rel_*` id arrays on entity docs, updated by painless script, with hand-picked exclusions for super nodes (3.3) | Unbounded document growth for hubs; write amplification on every relationship | Avoid; use indexed join/edge tables. Keep the idea of not materialising hub-side reverse lists |
| S6 | Representative `observable_value` computed at read time and as a runtime script field (2.3) | Sorting cost at query time; two implementations to keep aligned | Store a generated/maintained `display_value` column per type |
| S7 | Keyword normalizer lowercases and folds accents; `ignore_above: 512` (3.2) | Case-insensitive id/value matching, but long values silently unsearchable by keyword | Normalise explicitly in value objects; use `text` with `CHECK` + B-tree on normalised form, or hash indexes for long values (URLs) |
| S8 | Deterministic UUIDv5 ids from canonical JSON, with the full STIX id kept as `standard_id` and an immutable UUIDv4 `internal_id` (1.1) | Good: idempotent ingestion, stable internal references across standard_id changes | Copy |
| S9 | Alternate STIX ids (`x_opencti_stix_ids`) consulted on every lookup; previous ids retained on upgrade and merge (1.9) | Good: ids from other producers keep resolving; merges are lossless for references | Copy, as a separate table with a unique index on the id |
| S10 | Hash-based identity picks one hash by precedence, but registers every hash as an alternate id and searches by any non-fuzzy hash (1.5) | Good dedup across partial hash sets; fuzzy hashes inconsistently included | Copy, but exclude fuzzy hashes from identity entirely |
| S11 | Stream events carry the full STIX object plus RFC 6902 `patch` and `reverse_patch` (3.5) | Consumers can be stateless; filters can be evaluated on before/after state; sync can detect `/id` changes | Copy the envelope (possibly wire-compatible with OpenCTI v4 events) |
| S12 | Stream trimmed to ~2,000,000 entries; older positions recovered by re-querying the database by `updated_at`, deletions not replayed (3.5-3.6) | Consumers that fall behind silently lose deletes | Use a bigint monotonically increasing outbox sequence with explicit retention; emit tombstones; document the retention horizon |
| S13 | One object per queue message, ordered by dependency depth, GraphQL call per object (3.7) | Simple and parallel, but very chatty; missing-reference retries needed because ordering across workers is not guaranteed | Accept bundle-level commands processed in one transaction where possible; resolve intra-bundle refs before persisting |
| S14 | Large events offloaded to object storage (3.5) | Keeps Redis bounded | Copy the idea if the outbox payload is large (artifacts, big containers) |
| S15 | Rollover by ILM at 50 GB primary shard or 75 M docs (3.2) | Needs `_index` tracking on every document | In PG, use declarative partitioning only for the largest types (e.g. hash partition by `internal_id`) |

## 4. Recommendations for Fennec (not OpenCTI behaviour)

All of section 4 is **[REC]**.

1. **Identity value object per aggregate**: each observable aggregate exposes `fn id_contributing_json(&self) -> serde_json::Value` with a fixed, typed field set (no generic map), canonicalised with an RFC 8785 implementation (for example the `serde_jcs` crate, or an in-house implementation tested against the vectors in 1.8), then `Uuid::new_v5(&OASIS_NS, bytes)` with `OASIS_NS = 00abedb4-aa42-466c-9c01-fed23315a9b7`. Store `standard_id` as the full `type--uuid` string (or `(stix_type, uuid)`), never the bare UUID (1.3).
2. **Keep three identifiers** like OpenCTI: immutable `internal_id` (prefer UUIDv7 for index locality; OpenCTI uses v4), recomputable `standard_id`, and an `alternate_stix_ids` table `(stix_id text primary key, aggregate_type, internal_id, reason enum {incoming, hash, merged, previous_standard})`. The primary key gives O(1) resolution and DB-enforced uniqueness, replacing Redlock (S1, S9).
3. **Decide the id policy per type** (open question): either reproduce OpenCTI ids exactly (needed for dedup parity with OpenCTI streams and syncs), or follow the STIX spec where OpenCTI diverges (File/X509/Artifact combination, Process v4, Software case, registry `key`). A pragmatic option: canonical `standard_id` = OpenCTI-compatible for the types where OpenCTI is correct, register the spec-compliant id as an alternate id, and do **not** reproduce the defects Q1-Q3 (registry key name, email `from_ref`, network-traffic refs) but compute the spec form there, registering the OpenCTI form as alternate if OpenCTI interop is required.
4. **Normalisation in value objects, before id computation**, documented per type: domain and email lowercase (as OpenCTI), hostname lowercase (OpenCTI does not, decide), IPv4 dotted-quad without leading zeros, IPv6 RFC 5952 compression and lowercase, MAC lowercase colon-separated (STIX schema form), hash hex lowercase with algorithm-name alias table (`sha256 -> SHA-256`), Software name lowercase only for the id (as OpenCTI), trim everywhere. Every normalisation that OpenCTI does not perform will produce ids that differ from OpenCTI's for non-canonical input; keep the as-received id as an alternate id to stay resolvable.
5. **Hashes**: separate `observable_hash (aggregate_type, internal_id, algorithm enum, value)` with a unique index on `(aggregate_type, algorithm, value)` for non-fuzzy algorithms; fuzzy hashes stored but never used for identity or merge (fixes the 1.5 inconsistency). Use the OpenCTI precedence `MD5 > SHA-1 > SHA-256 > SHA-512 > SHA3-256 > SHA3-512 > SSDEEP > SDHASH > TLSH > LZJD` only if OpenCTI parity is chosen; otherwise restrict to non-fuzzy algorithms.
6. **Upsert/merge as domain commands**: `ObservableUpserted`, `ObservableMerged { target, sources }`, `StandardIdChanged { previous, current }` events; merges executed in one PG transaction (relationship redirection by `UPDATE ... SET from_id = target WHERE from_id = ANY(sources)` plus duplicate cleanup), with a confidence-based field policy equivalent to `upsert-utils.js:529-561`.
7. **Outbox + stream**: `domain_event` table (`seq bigserial`, `aggregate_type`, `internal_id`, `event_type`, `stix jsonb`, `patch jsonb`, `reverse_patch jsonb`, `origin jsonb`, `created_at`) written in the same transaction; publishers read by `seq`. Expose an SSE endpoint mirroring OpenCTI semantics (`id`, `event`, `data` with `version`, `type`, `data`, `context.patch/reverse_patch/sources`, `origin`, `message`) so OpenCTI's sync manager could consume Fennec directly, if wire compatibility is desired.
8. **STIX export**: reproduce the two OpenCTI extension-definitions verbatim (`ea279b3e-...` core, `f93e2c80-...` SCO) for round-trip compatibility; for custom SCO types prefer proper per-type extension-definitions but accept OpenCTI's `new-sco` + top-level-field form on input.

## 5. Open questions for the design

1. Id policy: strict OpenCTI parity, strict STIX 2.1 spec, or hybrid (spec + OpenCTI ids as alternates)? This determines File, X509, Artifact, Process, Software, Windows-Registry-Key, Email-Message and Network-Traffic ids.
2. Should Fennec reproduce OpenCTI's apparent defects (registry key canonical key `attribute_key`, email `from_ref` ignored, network-traffic refs embedded as objects) to match OpenCTI ids, given they are inferred from code and not runtime-verified here?
3. Should hash values be lowercased before id computation (diverges from OpenCTI and from tools emitting upper-case hex), or kept as received with a case-insensitive lookup index?
4. Should Hostname be lowercased like Domain-Name (OpenCTI does not)?
5. Is wire compatibility with the OpenCTI live stream (event version 4, SSE format, extensions) a goal, so OpenCTI instances can sync from Fennec?
6. Which OpenCTI-only top-level SCOs (`Email-Mime-Part-Type`, `Windows-Registry-Value-Type`) should become aggregates versus value objects embedded in their parent aggregates (as in STIX)?
7. Retention horizon for the event stream and whether consumers that fall behind must be able to replay deletions (OpenCTI recovery does not).
